01 — Objectives

Why this exists

Claude assistants answering ServiceNow technical questions from training memory risk being confidently wrong — plugin names, table names, and role requirements drift every release. The objective was to force every answer to be traceable to a real, citable source.

🎯 Ground answers in real docs

Retrieve from ServiceNow's official GitHub documentation mirror before responding, instead of answering from AI training memory. Every claim carries a citable docs.servicenow.com URL.

🖥️ Two working surfaces

A production tool, not a one-off: /servicenow_rag for Claude Code, and a parallel Project Instructions setup for Claude Desktop — both installable by any colleague via a shared internal repo.

📐 Prove it, don't assert it

Build a repeatable, scored testing framework — fixed questions, ground truth, PASS/PARTIAL/FAIL rubrics — so "did the instructions get better?" is a measurement, not a judgment call.

🔍 Fix what's broken upstream

Where the framework surfaces a real defect in the documentation mirror itself, escalate it with reproducible evidence and verify the fix — not work around it silently.

Guiding principleCarried into this session

This RAG path is now critical, company-wide functionality. The standing rule for all new work: verify, never infer. No path, folder name, or behavior ships on a pattern or a memory — it gets a live probe and the result is recorded.

02 — Origin Story

The defect that started the testing discipline

Before instruction tuning began, exhaustive integrity sweeps across four documentation bundles (ITOM, ITAM, ITSM, Platform — ~8,400 files) found a silent, mirror-wide failure mode.

20–32%
of files per bundle returned HTTP 200 with zero bytes of content
~2,200
empty files found across ~8,400 swept
→ 6
empty files remaining after the mirror team's fix, re-verified live
0
error signal — retrieval tools had no way to detect the failure themselves
Why this matters more than a normal 404

A 404 is a clean signal a fetcher can react to. An HTTP 200 with empty content looks like success — a retrieval tool has no error to catch, so it improvises. That's a direct hallucination trap, and it's the exact failure class this whole testing program exists to catch before it reaches a customer answer.

Escalated to ServiceNow's mirror documentation team with reproducible evidence; root-caused as a build bug and republished. Verified with a full before/after re-sweep — not taken on faith. Two smaller structural issues (content misfiled under the wrong bundle; oversized monolithic indexes) remain open with the mirror team.

03 — Architecture

How a question becomes a cited answer

Same retrieval discipline, two surfaces. Claude Code uses a slash command with its own fetch tool; Claude Desktop uses Project Instructions plus a local fetch MCP connector — the only tool either surface is allowed to use for retrieval.

Match topic to the correct doc bundle before fetching anything — e.g. CMDB → servicenow-platform, Discovery → it-operations-management.

02
Known-locations first
Check a curated list of confirmed-live direct paths before paging any index — skips megabyte-scale bundle indexes entirely when possible.

03
Bounded index navigation
If no known path exists, page the bundle index under a hard cap — 3 chunks with no match, or a bracketing search — never an unbounded crawl.
→
04
Fetch & cite
Fetch the target file directly from the raw mirror. Cite only the canonical docs.servicenow.com URL from the file's own frontmatter — never a remembered or guessed path.
→
05
Community as tier 2
Scoped site: search of ServiceNow Community as corroboration only — flagged "peer-authored," never overriding a documented API signature.

Hard boundaries — enforced, not suggested

🚫 No directory listings

The GitHub Contents/tree API, repo browse pages, and any equivalent bulk-discovery route are banned outright — discovery has exactly three sanctioned paths, and a directory listing isn't one of them.

🔒 Citation integrity

Only a document actually fetched this session may be cited. A path harvested from another page's link list is a pointer, not a source, until it's fetched itself.

🧭 Sole retrieval tool

Both surfaces are restriction-verified to a single fetch tool — no web search substitutes for mirror retrieval, no Bash, no filesystem read.

04 — Testing Methodology

A scored harness, not a vibe check

Every instruction change is evaluated the same way: fixed questions, live-derived ground truth, an explicit PASS/PARTIAL/FAIL rubric per question, run cold and in triplicate.

39
cold, serial evaluation runs in the last full baseline cycle
9→16
scored questions, each isolating one specific retrieval mechanism
n=3
replicates per question — a single run can't tell a real pass from a lucky one
132.7M
tokens measured across the window, 95% served from cache

Why replicates matter — the suite has caught intermittent failures before

Question A split PASS/PARTIAL/PASS across three identical runs. A known-locations regression fired in 1 of 3 replicates. A citation-fidelity issue appeared in 2 of 3. A single-shot test would have called every one of those "settled" and been wrong.

Components of the harness

  • Graded question set — each question isolates one mechanism (offset-jump recovery, citation integrity, index paging cap, directory-listing ban, gap-statement discipline).
  • Ground truth — verified live: exact byte counts, exact attribute names, and confirmed absences, not assumed ones.
  • Explicit rubrics — anchored to observable conditions ("lands on file X, pulls companion file Y"), not subjective quality.
  • A version-independent design — a new instruction revision is graded by pointing a new arm at the same suite; nothing about "what good looks like" is re-derived.
Cost efficiency82% saved

Prompt caching served 95% of all tokens. List-price equivalent for the full window: ~$109; the same workload without caching would have cost ~$596. That efficiency is what made 39 cold runs plus a full re-baseline affordable in a two-day cycle.

05 — Performance Results

Instruction v4 vs. v3 — accuracy held, cost dropped

Four regression questions (A–D) ran identically in both instruction versions. Same accuracy on three of four; retrieval cost — measured in fetch "hops," i.e. tool calls to reach the answer — dropped sharply on two.

Hops = tool calls (fetches) to reach a scored answer, median of 3 replicates per question per arm. Bar length indexed to the suite's largest median (v3-B, 12 hops). All 8 question-arm pairs scored 3/3 PASS or better — no accuracy tradeoff behind the cost numbers. Source: desktop-v4-test-script-2026-07-29.md §7 summary table.

📉 B — largest gap in the suite

v4 cost 4/4/5 hops vs. v3's 9/12/15 — v3 pays 2–3× the hops for the identical verdict. Both arms independently caught a stale "file is empty" note and routed around it.

📉 C — absence proven cheaply

v4 states the gap in 1–2 mirror hops; v3 proves the same absence by brute-force sweeping up to 8 files. Same conclusion, very different cost.

⚖️ A / D — no regression, honestly reported

A is a statistical tie; D is the one question where v3 is marginally cheaper (3 vs 4 hops) on a small single-heading file. Reported as-is — the results aren't cherry-picked to only show wins.

Counter-intuitive finding worth repeating live

Instruction length does not predict retrieval cost. The current instruction set is 12% longer than its predecessor yet cheaper in fetch hops on three of four regression questions. "Trim it to make it faster" was tested directly and the hypothesis inverted.

Honest reporting standard

Not every mechanism is declared a win. Citation integrity is reported conditional — clean on one question class, violated on another — with the counter-example named rather than smoothed over. Offset-jump is reported as a real improvement whose net cost, measured against baseline, is still a cost, not yet a win.

08 — Roadmap

What's next

Phase 1 — Pilot

ITSM end-to-end

Harvest live ITSM paths, write its 5 questions from Community threads, derive full ground truth on 2 deep questions — locks the template before it repeats across 6 more topics.

Phase 2 — Remaining topics

Platform, AI, ITAM, Build, Edge

Same process applied per topic, each batch approved before it's used for scoring.

Phase 3 — Pre-ship baseline

Attribution before shipping

n=1 baseline run on every question that targets a newly-added path — the only evidence that the coverage change itself caused an improvement.

Phase 4 — Ship

Both surfaces, measured cap

Code command grows freely; the Desktop instruction block's size ceiling is measured empirically, not guessed — additions ranked by value, stopped where a migrated question would regress.

Phase 5 — Score

Full matrix, full ledger

n=3 across all 36 questions, verdicts recorded topic-by-topic so a session break never loses more than the batch in flight.

Goal verification — what "done" means

All 36 questions carry a recorded verdict · all 5 newly-targeted paths appear as an actual fetch in a run sidecar, not just in question wording · the harness exits green on a live-served instruction set · no previously-passing question regresses. Coverage bought at the cost of adherence does not count as done.
