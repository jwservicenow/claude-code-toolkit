Takeaway

Desktop RAG (published Project Instructions)
Use Sonnet, thinking medium. Opus costs more and answers no better — don't bother. Haiku is fine for quick triage but never cite it in anything customer-facing. Roughly 460 questions/month on a $50 allowance. Weak spot: questions that compare two products or span two doc areas — it can miss the part that actually distinguishes them.

Claude Code RAG (/servicenow_rag)
Use Opus, thinking medium. Sonnet is not enough here — it gets things wrong, not just thin. Leave thinking on medium; high costs 40% more for nothing. Roughly 140 questions/month on $50.

Both groups, one habit: if the answer says a page was cut off, longer than its window, or that something "isn't documented" — don't accept it. Tell it to re-read the file deeper. That's our single biggest source of wrong answers, and it's the one thing a user can catch in the moment.

The short version

We run two assistants that answer ServiceNow product questions by retrieving from the official documentation mirror. We did not know which underlying model either one needed, or whether turning up the model's "thinking" setting made the answers better. Both questions have a real monthly bill attached.

So we ran the grid: three models × two thinking levels × three questions × both assistants — 30 measured runs, each graded against written ground truth and priced from its own token records.

1. The two assistants need different models. The Desktop assistant hits its accuracy ceiling at Sonnet with medium thinking — $0.108 per question — and spending 2.4× more on Opus buys nothing. The Code assistant does not reach that ceiling until Opus, $0.350 per question.

2. Thinking level is not a reliable lever. In three of four medium-vs-high comparisons it changed accuracy by zero or slightly negative, while costing 8–44% more. It helped in exactly one place — the assistant that was already failing — and even there it made the model more careful, not more capable.

3. The Code assistant's gap is a retrieval bug, not a model deficiency. It truncates one documentation page at 6,000 bytes and never reaches the paragraph that answers the question. Fixing that instruction is almost certainly cheaper than buying a bigger model.

1 · Approach — what was built and why

The question, before any mechanism

We maintain two assistants that answer ServiceNow questions from a mirror of the official product documentation. They exist so that answers are retrieved and cited rather than recalled from a model's training — which matters because much of what we produce ends up in front of customer technical teams and has to be traceable to a source.

Each assistant is driven by a long block of written instructions telling it where to look, in what order, what to do when the docs don't cover something, and how to label anything that came from a community forum rather than official documentation. Those instructions are the product. The underlying model is a setting.

This sweep answers which setting to pick: which model, at which thinking level, for which assistant — chosen on accuracy per dollar rather than on instinct.

The two assistants ("arms")

The Desktop arm is the assistant published as Project Instructions for Claude Desktop. It has exactly one retrieval tool: a raw HTTP fetch. It reads the mirror directly, and when it wants to search the open web it fetches a search engine's lightweight page — which frequently returns a bot-challenge screen instead of results. Its instruction block is the live published guide, 18 KB of text.

The Code arm is the /servicenow_rag slash command used in Claude Code. It has the same fetch tool plus a real web-search tool, and its instructions include a multi-step fallback ladder for when the mirror comes up short. Its instruction block is 364 lines.

You would reasonably expect the Code arm to do better — it has strictly more retrieval capability. It does not, and section 3 explains why.

Stated fidelity deviation

The Code arm was measured as a subagent whose system prompt is the /servicenow_rag command text carried verbatim — not as a literal slash-command call on the main thread. This was necessary: a slash command has no per-run thinking setting and no guaranteed run record, and both are required to measure anything. The instruction text is byte-identical; the execution context is not. The Desktop arm uses the same technique (published guide text → subagent), so the two arms stay methodologically symmetric.

The grid — and why it is five cells, not six

Three models — Haiku 4.5, Sonnet 5, Opus 5 — at two thinking levels, medium and high. That would be six cells. It is five, because Haiku 4.5 does not support a thinking-effort setting.

We confirmed this by reading the shipping Claude Code binary rather than the documentation: the capability check hard-codes Haiku 4.5 to unsupported, and — importantly — an unsupported level is silently downgraded, not rejected. A "Haiku high" cell would have been an unlabelled duplicate of "Haiku medium," producing a fake data point that looked real. So the Haiku row is one cell, Haiku contributes to the model axis and the cost curve but not to the thinking verdict, and this document says so wherever that verdict appears.

Thinking-off was not tested — a deliberate scope call. The practical choice in front of us is medium versus high, not whether to reason at all.

5 cells × 3 questions × 2 arms = 30 runs.

The three questions, and what each is for

Three, not one, because a single question cannot distinguish the ways an assistant fails. Three, not ten, because each run costs real money and the marginal question was not worth more than the marginal cell.

IDQuestionWhat it tests
K "What features and functionality is provided by the plugin Event Management Core?" A naming trap. The app literally called Event Management Core (sn_em_ai) has one documented line — "Enables you to track and monitor alerts in the ServiceNow Agent Workspace" — buried in a dependency table the assistant isn't routed to. Right next to it sits the main Event Management app (com.glideapp.itom.snac) with pages of features. Answering with the big, impressive, wrong feature list looks like a great answer. Separates assistants that retrieve from assistants that pattern-match.
J "How to setup Now Assist for ITOM?" Deep, multi-hop procedural. The answer spans four documentation pages; a prior run needed eight fetches to assemble it. Where raw model capability should show loudest.
BUILD-4 A real Studio error: "Sorry, there was a problem on my side trying to complete this request." A known documentation gap — the mirror documents that error string nowhere. The right answer says so, then gives what is documented. Tests stop-and-state discipline. A weak assistant fails this differently than it fails J: it invents a root cause.

How the thinking level was actually set

Each arm got two variant definition files, identical in every byte except a single frontmatter field: effort: medium or effort: high.

This mattered more than it sounds. The obvious alternative is to write "think hard about this" into the question. That would have been wrong — the entire purpose of this harness is measuring how well an assistant follows its written instructions, so injecting extra instruction text into the task contaminates exactly the thing being graded. The frontmatter field changes the model's reasoning budget while leaving the instruction block byte-identical across cells, which is what makes a medium-vs-high comparison mean anything.

The field name, its accepted values, and Haiku's lack of support were all verified against the shipping binary (Claude Code 2.1.226) rather than assumed from documentation.

Why cost was measured by a separate script

The grader is fixture-pinned — six frozen run records prove it behaves identically every time. Adding token-and-dollar columns would have forced re-verifying all six fixtures for a metric that has nothing to do with retrieval grading. So cost lives in a separate read-only script reading the same run records. The grader was never modified.

2 · Testing technique — how the measurement was made trustworthy

This is the section that separates a real result from a plausible-sounding one.

The grader reads the machine record, not the model's account of itself

The grader reads each run's sidecar — the harness's own log of every tool call the model made, with the arguments it passed and the bytes it got back. It never reads the model's prose.

That distinction is the whole ballgame. An assistant writing "I fetched 6 files from the mirror" is not evidence it fetched 6 files. Several runs in this sweep printed a tidy self-reported metrics block at the end of their answer; not one of those numbers was used.

This is how we caught the central defect

Two Code-arm runs stated they had checked the relevant page and found nothing. The record shows they fetched that page with a 6,000-byte cap on a 16,605-byte file. They had not checked it. They had checked the first third of it.

The leak gate

Each arm is restricted to a specific tool set — Desktop to fetch only, Code to fetch plus web search. If a run reaches for anything else, the grader VOIDs it. A voided run is re-fired, never patched — you cannot clean up a run that touched a tool it shouldn't have, because you cannot know what it learned from it.

All 30 runs came back clean. Zero VOIDs, zero re-fires.

There is also a hard gate on fabricated citations: any run inventing a documentation URL absent from the bytes it actually retrieved is an automatic FAIL regardless of how good the prose is. Every citation that looked like it might have come from memory rather than a fetch was checked against the run's retrieved bytes. None were fabricated.

Fixture pinning, before and after

Six frozen run records are pinned by checksum; re-grading them asserts the outputs are unchanged. It passed before the sweep and again after — so grader drift mid-sweep would have been caught rather than published as 30 rows of quietly inconsistent scores. The cost script has the same kind of pin: one fixture prices at $0.3080, before and after the one change made to it.

The one mid-sweep change, and why it was safe

The Haiku runs came back priced as "model not in pricing table." The run records report claude-haiku-4-5-20251001; the pricing table's key is claude-haiku-4-5; exact string match missed. The fix changed the lookup to match on the longest table key the model id starts with. Rates untouched, grader untouched, and the fixture pin confirmed the exact-match path still produced an identical number. Approved before it was applied.

The accuracy rubric

Three buckets, judged on the answer text against written ground truth. Deliberately coarse — this is a judgment call applied against a written standard, not an automated score, and pretending otherwise with a 0–100 scale would be false precision.

  • PASS — reaches the ground truth's substance, grounded in retrieved content, no fabrication. On BUILD-4, a correct stop-and-state — "the docs don't cover this, here's what they do cover" — is a PASS. A deliberate call: correctly reporting a gap is the behaviour we want, not a consolation prize.
  • PARTIAL — substantively correct but incomplete, or correct with an ungrounded aside.
  • FAIL — wrong, fabricated, or (on BUILD-4) inventing coverage that doesn't exist.

Scored PASS = 1.0, PARTIAL = 0.5, FAIL = 0 for the cell means.

We found a defect in our own ground truth

BUILD-4's ground truth carried a FAIL condition saying that naming the plugin id sn_now_creator as documentation-sourced was an automatic failure, because a re-check had found that string nowhere in the mirror.

That re-check was wrong. sn_now_creator is in the mirror, in the install page's procedure, step 4. The earlier check missed it because raw documentation markdown escapes underscores — the file literally contains sn\_now\_creator, so a search for sn_now_creator returns zero hits. The fetch tool strips those escapes before the model sees the text, so an assistant reading that page reads the real plugin id and is correctly citing official documentation. Our grep tested a string the file does not contain, and concluded the file does not contain the plugin.

Re-verified live 2026-08-09 across all five relevant files with escapes stripped: sn_now_creator appears once. sn_gen_ai_controller and the error code MISSING_DEPENDENCY genuinely appear nowhere — so those halves of the condition stand.

One run's verdict changes: O-H-B4-code moves from FAIL to PASS. It cited the plugin correctly and we would have marked it wrong. The ground-truth file itself has not yet been edited; until it lands, the results doc is the authority.

Worth stating plainly rather than quietly fixing, because it is a live methodological lesson: the harness's own reference data needs the same verification discipline as the runs it grades. A grading rule that has never been re-derived is an assumption wearing a uniform.

How cost was measured

Per-turn token counts come straight from each run's own usage records — input, cache-read, cache-write (5-minute and 1-hour rates handled separately, since they price differently), and output — multiplied by that model's published rates. Sonnet 5 is inside an introductory pricing window through 2026-08-31, so both list and introductory prices were computed throughout, and every recommendation here is made on list price, so it survives the intro rate expiring.

A known data defect biases all costs low

Some run records report a stale output-token count — one 2,022-character final answer records 3 output tokens; a pinned fixture's 4,426-character answer records 7. The cost script reads the field correctly; the recorded value is wrong. Every dollar figure here undercounts output. Relative comparisons between cells hold as long as the bias is uniform, which we have not verified. Treat absolute dollars as a floor.

The pilot gate — proving the thinking knob was turning, not just declared

Before spending the remaining runs, one cell went end-to-end to prove "medium" and "high" actually produce different behaviour. Confirming the setting exists is not the same as confirming it does something.

The first attempt used question K and found nothing — the axis was flat. That was the right thing to discover at 3 runs rather than 30, and the response was not to declare success: it was to stop, and re-gate on the harder question J with two runs per level on both arms.

On J the separation was clean. Measured as thinking blocks per assistant turn, medium ran 0.33–0.75 and high ran 0.80–1.00, with no overlap across 8 runs on both arms. The knob turns.

Two honest caveats. First, the reasoning text is stripped from run records (signature only, zero characters), so depth is genuinely unobservable and blocks-per-turn is a proxy. Raw block counts alone are confounded by turn count, which is why the ratio is used; output tokens overlap between levels and discriminate nothing.

Second — and this matters for reading the verdict — the metric saturates. It separated on Sonnet on question J. On Opus, and on the easier questions, it pins near 1.00 at both levels and tells you nothing. Haiku sits at exactly 1.00 on every single run, consistent with a fixed reasoning level you cannot set. The thinking verdict is question-difficulty dependent. On a question that doesn't strain the model, the axis is null and no amount of measurement will make it otherwise.

What was deliberately excluded

Quote fidelity — whether a run's quotations match the source byte-for-byte — was measured, calibrated, and closed as permanently report-only on 2026-08-09. It is not a verdict input in this sweep and should not be re-opened as one.

Known limits of the method

  • n = 1 per cell per question. Four replicates exist on question J only. One borderline judgment can move a cell mean by 0.17.
  • Three questions is a narrow sample, and question K carries an outsized share of the signal — most Code-arm failures are the same question failing repeatedly.
  • The mirror is a moving target. Ground truth was spot-checked live during this sweep — which is how the sn_now_creator defect surfaced.
  • Cross-arm cost is not summable. The Code arm's web-search hops bill differently from mirror fetches.
  • The thinking axis rests on two models, not three, because Haiku has no effort knob to turn.
  • Absolute dollar figures are biased low by the output-token defect above.

Why the better-equipped assistant did worse

This is the surprise, and it deserves stating rather than burying: the arm with strictly more retrieval capability scored worse at every model size. The Code arm has real web search; the Desktop arm has to scrape a search page and usually gets a bot challenge. And the Code arm lost.

The mechanism is specific and unglamorous. Question K's answer lives in one line of a dependency table on a 16,605-byte page, under a heading about two-thirds down. The Code arm's instructions lead it to fetch that page with a byte cap — 6,000 bytes in the Sonnet runs. It reads the first third, doesn't find the line, and concludes the documentation doesn't cover the plugin. It then fills the gap from web search and a store listing, and — in the weaker cells — hands back the neighbouring product's impressive feature list as though it were the answer.

The Desktop guide does not have that habit. Haiku on the Desktop arm answered question K correctly in two fetches for three cents — beating every Code-arm cell including Opus-high at $0.496. That is not Haiku outperforming Opus. That is one instruction set routing correctly and the other truncating.

Three of four comparisons show no gain or a small loss, at 8–44% extra cost.

The one large gain is instructive rather than encouraging. High thinking on the Sonnet Code arm rescued the BUILD-4 answer (the medium run routed to the wrong documentation folder and lost the deprecation notice; the high run did neither) and softened the K answer from FAIL to PARTIAL — the high-thinking run explicitly flagged all its substitute content as unverified and advised against citing it, where the medium run had asserted that two different products "describe the same product." More thinking made the model more careful about what it claimed. It did not make it fetch more of the file. The underlying retrieval defect was untouched.

The Opus-Code regression from 1.00 to 0.83 is one run flipping on one ungrounded aside at n=1. It is not evidence that thinking hurts; it is evidence that the axis sits inside the noise band at this sample size.

Practical guidance: do not set high thinking as a default. Set it when a specific arm is underperforming, and then verify it actually moved something.

What I'd do differently

  1. Fix the truncation before buying the model. The highest-value change out of this sweep is not a model setting — it is amending the servicenow_rag instructions so that a page fetched under a byte cap which does not yield the answer gets re-fetched further in, rather than being declared exhausted. Three of the four question-K misses across the entire grid trace to that one behaviour. If that lands, the Code arm's curve needs re-measuring from scratch, and Opus may stop being necessary.

    Update 2026-08-09 — that change landed. A TRUNCATED-READ RE-FETCH rule is now in both instruction sets (commit b71e4ae, jwservicenow/claude-toolkit), along with the missing azure-discovery-methods-platcap.md known location. Nothing on this page has been re-measured against it — the recommendations still describe the pre-amendment instructions. Re-firing question K on Code and AZ on Desktop (~$0.50–0.90) is what would tell us whether Opus is still needed on the Code arm. The Desktop half of the fix is inert until the updated instruction block is pasted into the Claude Desktop Project Instructions.
  2. Run n ≥ 3 on the cells that matter. At n=1 a single ungrounded sentence moves a cell mean by 0.17 — the same size as the entire Opus thinking effect. The four replicates we do have were the only reason the thinking gate could be trusted at all.
  3. Pick harder questions for the thinking axis specifically. The axis is null on questions that don't strain the model — we learned that by burning a pilot on question K and finding nothing. Gate the thinking axis on the hardest question first, not the cheapest.
  4. Re-derive ground truth as part of the sweep, not before it. The sn_now_creator defect had been sitting in the reference data since 2026-08-08 and would have silently mis-graded a correct answer as a failure.
