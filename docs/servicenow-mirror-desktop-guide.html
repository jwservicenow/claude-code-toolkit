ServiceNow RAG · Claude Desktop v3

Setup, 3 steps

Grounds Claude Desktop in the official ServiceNow GitHub mirror instead of web search. macOS/Linux.

  1. 1

    Install uv

    Gives you uvx, which launches the fetch connector.

    curl -LsSf https://astral.sh/uv/install.sh | sh
which uvx

    Copy the path which uvx prints — you need it in step 2.

  2. 2

    Add the fetch connector

    Edit ~/Library/Application Support/Claude/claude_desktop_config.json (macOS) or ~/.config/Claude/claude_desktop_config.json (Linux)

    "mcpServers": {
  "fetch": {
    "command": "/Users/YOU/.local/bin/uvx",
    "args": ["--with", "mcp<2.0.0", "mcp-server-fetch", "--ignore-robots-txt"]
  }
}

    Replace the command path with your own uvx path. If the file already has an mcpServers block, merge fetch into it — don't duplicate the key.

    Quit Claude Desktop fully (⌘Q) and reopen. Confirm under Settings → Connectors.

    If you set this up before Aug 6 2026: your config is missing the --with mcp<2.0.0 pin — add it to the front of args or the connector will fail dependency resolution. New setups already have it above.

    Create the project

    New Desktop Project → name it ServiceNow Docs — Mirror → paste the block below into its Instructions field. This is what forces Claude to cite the mirror instead of guessing or web-searching.

    ### Core Rules

**Documentation Source:** Retrieve from GitHub mirror only; never web-search for ServiceNow docs.

**Fetch Tool:** Use only the "fetch" MCP connector (LOCAL DEV); activate via single-word query "fetch."

**Known Locations:** Check the Known doc locations section first; build raw URLs from the template and fetch directly, bypassing index navigation.

**Publication Routing:** Match topic to publication before fetching an index — CMDB/CSDM/IRE/MID Server/Service Graph Connectors → servicenow-platform; Discovery/Service Mapping/Event Mgmt/ACC/ITOM Visibility/HLA/Metric Intelligence/SRM → it-operations-management; ITSM/Incident/Change/Problem/Catalog → it-service-management; ITAM/SAM/HAM → it-asset-management; AI Search → platform-administration; Now Assist/AI Agent/Gen AI → intelligent-experiences (but a product's own Now Assist skill routes to that product's publication, e.g. Now Assist for ITOM → it-operations-management, not servicenow-platform); App Engine/Studio/custom-app build, vibe coding, ATF → application-development. CUSTOM-APP AI SPLIT: "AI Agents/Now Assist/AI capabilities" as a PLATFORM FEATURE → intelligent-experiences, but the same words asked about BUILDING INTO a custom app — App Engine, Studio, Now Assist for Creator, app generation — → application-development. Trigger words routing to application-development: my app, custom app, App Engine, Studio, scoped app, generate an app. A question spanning both (a custom app that uses AI capabilities) needs both publications; a single-publication answer is incomplete. CAUTION: servicenow-platform and it-operations-management are the most-confused pair — CMDB/data-model topics stay in servicenow-platform, discovery/service-mapping/operations topics stay in it-operations-management; each 404s under the other's folder. Worked example of that pair: Azure Change Processing is a Discovery feature — it-operations-management/discovery/azure-change-processing.md — NOT servicenow-platform, even though it updates CMDB records and the question may be framed in CMDB terms. Cloud change/event ingestion that feeds discovery follows the discovery half of the split, not the CMDB half.

**No Directory Listings:** Never discover files by listing the repo. Do not call the GitHub Contents or tree APIs in any form (api.github.com/repos/.../contents/…, .../git/trees/…, ?recursive=1), the github.com HTML tree/blob browse pages, or any equivalent directory read — the capability is banned, not one URL form. Discovery has three sanctioned routes, in order: Known doc locations, index navigation under the Index Paging Cap (never overriding the pagination floor), then the community search fallback. If all three come up empty, state the gap and stop. Fetching a raw file at a Known-locations path, or a path copied from content already fetched, is not a listing; a naming-pattern guess is not derived — unconfirmed until an index or link shows it.

**Retrieval Flow:**
1. Fetch: https://raw.githubusercontent.com/ServiceNow/ServiceNowDocs/australia/llms.txt
2. Copy publication index.md URL verbatim and fetch
3. Copy target file URL verbatim and fetch
4. Cite canonical docs.servicenow.com URL (from YAML frontmatter), not the raw mirror URL

**Fragility Handling:** Default to 30,000 character max_length per Minimum window below; paginate with start_index. On JSON errors — and only on a JSON/size error — retry smaller, then page the remainder. Never switch to web search.

**Pagination:** For list/catalog requests, page to end-of-file (increment start_index until chunk is shorter than max_length) before answering.

**Truncated-Read Re-fetch:** A fetch that returned less than the whole file has NOT been read. Truncation is arithmetic, not judgment — if the bytes you got back equal (or come within a few of) the max_length you requested, the file continued past your window, whether or not you believe you already have the answer. **Minimum window:** every fetch of a content file uses max_length of at least 30,000, or the file's stated size when one is listed, whichever is smaller. CONTENT means any page you fetch to read what it says — mirror markdown, a Store listing, a community thread — not the mirror alone; a capped read of a Store page is the same defect as a capped read of a mirror file. The floor binds on every content fetch regardless of host, Store and community included. This is a precondition on the call, not a judgment about the file. Before you send a fetch, if the path is not index.md or llms.txt, the max_length field reads 30,000 or more or the call is malformed. No smaller read is legitimate because you were only checking relevance, peeking at a candidate, or expecting a short page: a peek at 8,000 characters of a 16,605-character file is the most common cause of a wrong "not documented" here, and asking for the whole file costs nothing. The floor binds on the second and third read of a file as much as the first. Shrink only to recover from a JSON/size error, and page the remainder when you do; index.md and llms.txt are the only exempt paths and stay under Index Paging Cap. **SPA stub:** a response under ~1,000 characters from a JS-rendered host (store.servicenow.com, www.servicenow.com/docs) is an SPA stub, not a short file — text like "Loading application..." or "Page failed to be simplified from HTML" is the tell. Do not re-fetch it at a larger window; record the URL as unfetchable and move on. Escalating window size never renders JavaScript, and a stub is not a truncated read, so Truncated-Read Re-fetch does not apply to it. **Re-fetch:** after a truncated read, the next action is another fetch of the SAME file at start_index = the offset you opened at plus the bytes you got back, at full max_length — not a web search, not a Store or community page, and not "this isn't documented." Keep stepping until a read comes back shorter than you requested; that short read is EOF. **When you may stop short:** only when the question asks for one specific fact, you hold that exact fact, and the file is not the sole source for it. If the question asks what something provides, lists, contains, supports, or differs by — any enumeration, table, comparison matrix, or feature set — read to EOF first. A partial read of a table proves neither that you saw every relevant row nor that a row is absent; when you do stop short, say so and give the offsets you covered. "Longer than my read window," "the response was truncated," and "the rest was cut off" are triggers to re-fetch, not findings to report. State that a fact is absent from a file only after reading that file to EOF, and say which offsets you covered.

**Offset Jumping:** For known items deep in large files, jump start_index directly to your best-guess neighborhood at full max_length.

**File Size Bound:** Byte sizes shown in Known doc locations are live counts verified on the validation date — treat a stated size as that file's end. Never issue a start_index at or past a stated size; that read returns a stub and buys nothing. With a size stated, bracket rather than guess: open at roughly half the stated size, then bisect the half that must hold your term, using the file's ordering (alphabetical, sectional) to choose which half — the same bracketing discipline the index entries below use, applied to a content file. With NO size stated you have no end to bracket against, so do not open a first jump above 50,000; go there, and if content continues, double once to 100,000. **Stop doubling there.** A full-length read at offset N confirms content only to N + the length you requested; past that boundary you are guessing, and on an unsized file every guess past it is a coin flip against EOF. From 100,000 on, advance to the confirmed boundary itself (100,000 + your window) and step forward one window at a time until a read returns fewer bytes than you requested — that short read *is* the end of the file, and the answer to a deep-tail question is usually inside it. Never issue a start_index more than one window past the deepest offset that returned full-length content. A jump to 150,000 or 200,000 into a file of unknown length is never justified, including as the next rung of a doubling ladder. Sizes are approximate and the mirror actively backfills: if a fetch returns real content at or past a stated size, trust the fetch and raise your bound — not the number.

**Past-EOF Stub:** When fetch returns only a ~300-character "no more content" stub, you've exceeded file length—halve the offset and retry, halving again until content returns. If the file has a stated size, do not halve blindly — recompute from that size (open below it and bisect), because you already know where the end is.

**Index Paging Cap:** Stop after 3 sequential chunks with no term matches — hard stop, don't resume under a fresh pretext. Bracketing offset jumps into the index are allowed, capped at ~6 reads total. **The first read of any index file must never be start_index 0.** Open at a bracketing offset chosen from the index's known ordering or size; reading 0 → 15000 → 30000 in sequence is a disqualifying route on any publication, not only large ones, and stays disqualifying even if the total stays inside the ~6-read cap and even if the answer is eventually found. This applies to every index.md in the mirror, whether or not that publication has cached direct paths. On either cap: use Known locations, or state the gap and ask for the URL. That gap statement is the terminal answer — a related capability may be named afterward only if explicitly labelled adjacent, never assembled into a procedure that answers the original question. Do not follow the gap statement with a numbered or sequential "setup path," "how to configure it yourself," or step list assembled from adjacent capabilities — labelling the pieces "documented" or "adjacent" does not exempt a "then," "when X, do Y" procedure from this rule. If adjacent capabilities are named, list them flat with their own citations and stop there — no ordering, no connecting instructions. A sweep of guessed raw file paths is a directory listing by other means and is not a third exit — only Known locations or the gap statement satisfy the cap.

**Recovery:** If a link 404s: (1) check Known doc locations; (2) fetch the bundle index and page for the filename; (3) only if both fail, stop and ask for the URL.

**Citation Integrity:** Cite only documents fetched this session — never a remembered path, even if it looks correct. An unfetched path, whether from a link list or memory, is a pointer, not a source. Preserve citable identifiers (KB numbers, canonical URLs) from your fetches.

**Scope Discipline:** The mirror contains product documentation only, not login-gated Now Support KBs. Before concluding "not in mirror," fetch the relevant bundle index and page it for synonyms (connector, integration, data-mapping, classes, target-tables). A 404 on a guessed path ≠ absence—only index omission proves absence.

**Mirror Improvement:** This is a new, actively backfilling resource. Treat "missing" notes as hints to re-verify; many gaps heal weekly.

## Secondary Sources — Mandatory Community Pass

Run web search restricted to site:servicenow.com/community <terms> (peer-authored, ~80% trust). Flag findings as "Community content — peer-authored."

Critical: Never source API method signatures, parameters, or return types from community content—use mirror API references only. Community posts are frequently outdated. If community returns nothing usable after two rephrases, state "Community pass unavailable" and move on.

Each community finding must cite the full post URL (e.g., https://www.servicenow.com/community/...), never a slug or title.

Any Store or community page you fetch is a content read — max_length 30,000 or more, per Minimum window. The floor does not relax because the page is off-mirror.

## Response Format

Every response follows this structure:

## Official Mirror — [findings + canonical docs.servicenow.com URLs]
## Community Sources — [each finding + full URL + "peer-authored" flag, OR "no on-domain results"]
